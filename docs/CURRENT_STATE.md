## 4. Existing API endpoints

All under `/api/v1/auth`:

- `POST /api/v1/auth/register` → creates user, returns JWT
- `POST /api/v1/auth/login` → verifies credentials, returns JWT
- `GET /api/v1/auth/me` → returns current user (requires bearer token)

Plus `GET /` and `GET /api/v1/health` on the root app.

**No employee, skill, project, or any other domain endpoints exist yet on the backend.** The frontend's `employeeService.js`, `projectService.js`, `recommendationService.js`, and `analyticsService.js` are all mock/in-memory implementations that simulate network latency with `setTimeout` and read from `src/data/*.js`. This is the primary Phase 2/3 gap — matches what the master prompt calls "the next major task."

## 5. Authentication status — ✅ solid, matches spec

- Registration and login both hash with bcrypt (via passlib) and issue JWTs (HS256, 60 min expiry) containing `sub`, `email`, `role`.
- `SECRET_KEY` and `DATABASE_URL` are read from `.env`, which is **not committed** (`.gitignore` present, `.env` correctly excluded from the audit trail). Good baseline hygiene.
- `get_current_user` dependency validates token signature/expiry, loads the user, and rejects inactive users (403).
- Frontend `AuthContext` restores session on load via `/auth/me`, stores JWT + normalized user in `localStorage`, exposes `isAuthenticated`, `isAdmin`, `isEmployee`, `login`, `register`, `logout`.
- Frontend route guards (`ProtectedRoute`, `RoleRoute` in `AppRoutes.jsx`) redirect unauthenticated users to `/login` and cross-role access to the correct dashboard.

## 6. Existing role authorization — ⚠️ partial, frontend-only

- Role redirection is enforced **only in the React route guards**. The backend has **no equivalent** — there is no `require_role("MANAGER")`-style dependency anywhere in `app/core/dependencies.py`, and no endpoint currently checks `current_user.role`.
- This isn't a bug today because there are no manager-only or employee-only backend endpoints yet — but it is a real risk the moment Phase 2/3 endpoints are added without a role-checking dependency. **This needs to be built as part of Phase 1/2, not deferred.**

## 12. Potential architectural problems to watch

1. **Missing role guard on the backend** — must land before any manager-only/employee-only route is added, not after.
2. **No unique constraint** on `(employee_id, skill_id)` or `(project_id, skill_id)` — should be added in the Phase 1 migration to prevent duplicate rows.
3. **`availability_status` is a single string** on `Employee` — the spec wants time-based availability tracking (an `Availability` table). Keep the string as a quick-glance status, add the table alongside it rather than overloading one field.
4. **Engine created with `echo=True`** in `database/postgres.py` — fine for dev, should be conditional on an environment flag before anything resembling production/demo polish (Phase 13).
5. **No repository/data-access layer yet** — acceptable now, worth introducing once Employee/Project/Skill CRUD lands so business logic doesn't leak into routers as the surface area grows.
6. **Frontend `services/*.js` mock modules and `data/*.js` files will need to be deleted/replaced in lockstep with each backend router landing** — doing this incrementally, one service at a time, keeps the app in a working state throughout (per Section 29's "no silent mass changes" instruction).

## 13. Recommended first implementation phase

**Phase 1 — Data model completion**, exactly as the master prompt orders it. Concretely, in order:

1. Add the missing SQLAlchemy models (Certification, EmployeeProject, Availability, Document, SkillGap, Recommendation, Team, Assignment, Notification) with proper FKs/indexes/constraints, building on the existing `Base`/naming conventions.
2. Add the missing unique constraints to `EmployeeSkill`/`ProjectSkill` in the same migration pass.
3. Generate and review Alembic migrations (autogenerate, then hand-check — this schema has enough FKs that autogenerate needs a human pass).
4. Add a `require_role()` backend dependency in `core/dependencies.py` now, even though it has nothing to protect yet, so every router built from Phase 2 onward uses it from day one.
5. Verify existing auth flow, migrations, and dashboards still work after the migration lands, before moving to Phase 2 (Employee module).

This does not touch anything already working — `auth.py`, `security.py`, `dependencies.py`'s existing function, the User/Employee/Skill/Project models, and all frontend auth/routing code are preserved as-is.
